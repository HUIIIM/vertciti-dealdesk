# DealDesk 产品团队章程 v1.0（2026-10-02，董事长指令）

> 董事长原话："你要有一个商品的逻辑，这个产品的逻辑在里面。产品的设计师在哪里？产品的架构师，产品的设计师，这些都要组好团队，确定好，要做好。"

## 一、为什么需要产品团队

此前 DealDesk 功能都是工程直给：需求→代码→上线。缺的是**产品逻辑**——
这个功能在 Miao 的 deal 工作流里处在哪个环节？解决他哪个具体痛点？
不用它他会怎么做？有了之后他的动作少几步？答不上来就不做。

## 二、编制（CPO 辖区）

| 角色 | 职责 | 铁律 |
|---|---|---|
| **产品架构师** | 功能在系统中的位置：数据从哪来、到哪去、与现有模块的关系、边界情况 | 任何功能必须先有架构位置图，无位置的不进开发 |
| **产品设计师** | 用户视角：Miao 的操作路径、每一步看到什么、信息层级、空/错/慢状态 | 任何界面改动必须先有设计说明（改哪里、为什么这样排），无设计的不进开发 |
| **工程** | 实现 | 只接架构师+设计师双签字的需求 |

## 三、产品逻辑（商品逻辑）

DealDesk 是 N=1 工具，只有一个用户：Miao。产品逻辑三问，每个功能立项前必须回答：

1. **环节**：intake（搜集）→ underwriting（测算）→ decision（决策）→ archive（归档），这个功能落在哪个环节？
2. **省步**：不用它 Miao 要点几下/查几个地方？用了之后少几步？省不出 3 步以上的功能不做。
3. **诚实**：数据来源标不标得出来？标不出来的不上（未知就是未知）。

## 四、流程

```
想法 → 产品架构师（位置+数据流）→ 产品设计师（操作路径+界面）→ 双签字
→ 工程实现 → 真机验证 → 上线
```

- 架构师和设计师互相 review：架构师看设计稿的数据能不能来，设计师看架构的输出用户看不看得懂。
- 董事长反馈的功能（如"图片要录入"），先由产品团队翻译成产品逻辑，再进工程——
  禁止工程直接按字面加按钮（2026-10-02 图片上传按钮事故教训）。

## 五、当前 backlog 的产品归属

- backlog 每个待做项由产品团队补"产品逻辑三问"后才能进每日改进排期。
- 竞品学习的 Top5（Comps/Tear Sheet/数据质量门/穿透树/动机分）已进 backlog，
  产品团队逐项出架构+设计，排期不变（每天一项）。
